# Profil explicite DLL v2

Utiliser tools/pulse_probe/restore_dll_bound.py avec les mêmes arguments d’opération que restore_operations.py. Cette entrée impose PHASE2_CHECKPOINT_BINDINGS_DLL_V2.json et le contexte poly-pulse-o2-state-dll-v2. Elle refuse un document rétrogradé vers le profil v1. Le fichier de bindings v1, ses enveloppes et pointeurs restent inchangés ; l’entrée historique conserve son profil non lié aux DLL. Aucun pointeur/reçu n’est migré implicitement : choisir une nouvelle racine pour v2.

Le contexte v2 ajoute l’empreinte canonique du [manifest de runtime](PHASE2_RUNTIME_DLL_MANIFEST_V2.json) aux empreintes moteur/patch/worker/libPulse/données/patient/configuration/horloge. Les bindings épinglent aussi les octets exacts du manifest. Les quatre états moteurs sont les mêmes, avec de nouvelles enveloppes techniques ; aucun état biologique ou nouvel état final n’est exporté.

Avant lancement, les fichiers libc++.dll, libunwind.dll et libwinpthread-1.dll doivent se trouver au chemin attendu avec leur SHA. Une copie homonyme à côté du worker ou dans son répertoire courant est refusée, même identique. Avant de transmettre le checkpoint, le contrôleur attend le dossier créé par le worker dans main, interroge ses modules avec les API Windows et vérifie les trois chemins/SHA ainsi que la présence et l’empreinte du worker. Tout autre module hors des répertoires système approuvés est refusé. Une erreur termine/récolte seulement l’enfant Popen possédé, sans envoi du checkpoint.

Les modules System32/SysWOW64/WinSxS sont approuvés par chemin sans empreinte de leurs octets. Ce contrôle a lieu avant stdin ; aucun chargement tardif après cette frontière, stockage hostile ou modification concurrente du runtime n’est qualifié. La preuve des modules est persistée et le marqueur CHILD_STARTED reste actif jusqu’à la fin réelle de l’enfant, avec ses protections contre la récupération d’un enfant vivant.

Le [protocole préalable](PHASE2_DLL_V2_PROTOCOL.json), les [résultats](PHASE2_DLL_V2_RESULTATS.json) et les [preuves](results/phase2-dll-v2-2026-10-18/README.md) couvrent quatre checkpoints, cinq horizons et neuf sorties : 180 comparaisons passent au seuil initial. À la preuve pré-input, engine.log et outputs.csv sont encore absents ; les trois DLL chargées ont été observées. Un masquage temporaire possédé par copie identique est refusé avant toute tentative puis retiré après vérification des octets. Un pointeur v1 est refusé sans modification. Deux appels CLI v2 donnent une tentative native supplémentaire et neuf comparaisons, puis un résultat relu.

Les 141 tests Python passent, dont 14 nouveaux : manque/changement, doublon et échappement du manifest, masquage, chemins et octets chargés, module inattendu/manquant, politique système, incompatibilités d’enveloppe/pointeur et refus de rétrogradation. Les tests de fichiers altérés/manquants utilisent des fixtures synthétiques ; le masquage identique et les observations de modules utilisent le vrai worker dans le workspace. Les deux runs et leurs sources sont conservés, le final intégrant le refus anti-downgrade.

La [qualification spécifique v2 de récupération](PHASE2_DLL_V2_RECOVERY.md) passe désormais 24 cas de transactions, morts de parent, refus et exclusion. Prochaine étape : timeout réel v2 et synthèse technique. Les matrices antérieures v1 ne sont pas promues automatiquement à v2. Cycle général de l’adaptateur, ancien guard sans transaction, fenêtre enfant avant identité, panne électrique/stockage, rollback général et redistribution restent ouverts. Canon, seuil, échec initial, main et PR #1 préservés ; aucun scénario biologique démarré.
